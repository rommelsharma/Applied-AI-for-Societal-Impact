# Private Corpus Guide (Local-Only Full Books)

This project ships with two parallel corpora:

| Corpus | What goes in | Where it lives | Committed to git? |
|---|---|---|---|
| `public` | Synthesised, retrieval-friendly book dossiers (concept-rich, concise) | `data/corpora/public/` | Raw PDFs are committed; derived artefacts are gitignored |
| `private` | Full-book PDFs you own personally (research / private demo only) | `data/corpora/private/` | **Never committed** - the entire directory is gitignored |

The reason for the split is honest evaluation. The public corpus stays
small, well-attributed, and reviewable; the private corpus lets you
measure how much retrieval lift the system gains from real, long-form
text **without leaking copyrighted content** into the public repo or any
deployed demo.

This guide is the operator-facing handbook for the private corpus.

---

## 1. Layout the code expects

Every corpus follows the same five-folder convention. The path resolver is
corpus-aware, so all you have to do is drop PDFs into the right `raw/`
folder and tell the pipeline which corpus to build:

```
data/corpora/<corpus>/
  raw/             # source PDFs (private: full books you own)
  parsed_text/     # generated by data_pipeline/pdf_parser.py
  chunks/          # generated by data_pipeline/chunker.py + concept_extractor.py
  knowledge/       # generated by data_pipeline/enrich_chunks.py
  vector_store/    # generated by data_pipeline/build_vector_index.py
```

Anything below `data/corpora/private/` is matched by the `.gitignore` and
**will not** show up in `git status` even if you accidentally commit it.

---

## 2. End-to-end build, private corpus

Run these from the project root, on the laptop where the books physically live.

```bash
# 1. Make sure your PDFs are in the right place
ls data/corpora/private/raw/
# noise-kahneman-sibony-sunstein.pdf, thinking-fast-and-slow.pdf, ...

# 2. Run the offline ingestion pipeline against the private corpus
python data_pipeline/build_knowledge_base.py --corpus private --profile book

# 3. Build the vector index against the private corpus
python data_pipeline/build_vector_index.py --corpus private
```

### Index-time embedding behaviour (public and private)

`build_vector_index.py` uses the same logic for every corpus. **By default** (`RAG_EMBED_SENTENCE_WINDOWS=true`):

- Each chunk’s `text` is split into sentences; for each sentence position the code builds a **local window** of up to **2×`RAG_EMBED_SENTENCE_RADIUS`+1** sentences (default radius **3** → up to **seven** sentences, fewer at chunk edges).
- Each window is embedded with **Titan v2**; vectors are **mean-pooled** and **L2-normalised** so the chunk still has **one row** in `embeddings.npy` / FAISS (aligned with `index_metadata.json`).
- **`RAG_EMBEDDING_MAX_WINDOWS`** (integer, default `0` = no cap) subsamples windows evenly when you need to limit Bedrock cost on long chunks or large private corpora.
- **`RAG_EMBED_SENTENCE_WINDOWS=false`** restores a **single** Titan call per chunk on the full `text` (legacy behaviour).

`vector_store/manifest.json` stores the effective window settings. Changing radius, window toggle, or max-windows **requires re-running** `build_vector_index.py` (same class of change as switching `BEDROCK_EMBEDDING_MODEL_ID`).

For the public dossier corpus the equivalent commands are:

```bash
python data_pipeline/build_knowledge_base.py --corpus public      # (or just default)
python data_pipeline/build_vector_index.py --corpus public        # (or just default)
```

Both corpora can co-exist on disk. The retriever, runtime detector, and
evaluation scripts pick which one to use via the `--corpus` flag or via
the `CORPUS_NAME` environment variable.

## 3. Running the runtime against a specific corpus

Three equivalent ways to pin the runtime to a corpus:

```bash
# (a) Environment variable (whole shell session)
export CORPUS_NAME=private
python -m notebooks.test_bias_detection

# (b) Inline env override (one command)
CORPUS_NAME=private python evaluation/run_evaluation.py

# (c) Explicit argument from your own script
from app.services.bias_detector import detect_bias_comparison
result = detect_bias_comparison("...", corpus="private")
```

`run_sample_comparison.py` and the bundled notebook both honour
`CORPUS_NAME` so you do not need to edit them to run on the private corpus.

## 4. Honest A/B evaluation across corpora

The dedicated comparison script is `scripts/compare_versions.py`:

```bash
# Whole evaluation suite (32 scenarios) on both corpora
python scripts/compare_versions.py --versions public,private

# Just two scenario ids for a quick smoke test
python scripts/compare_versions.py --versions public,private --scenario-ids 11,12
```

It writes:

* `evaluation/version_comparison_<timestamp>.json` - full per-scenario payloads (kept locally, not designed to be shared).
* `evaluation/version_comparison_<timestamp>.md` - reviewer-friendly markdown summary that includes counts and named biases only. Raw private-corpus excerpts are intentionally **not** in the markdown so the report stays safe to share.

When you publish numbers in the design document or your portfolio, the
recommended convention is:

* Use the **public corpus** numbers when the report will be public.
* Use the **private corpus** numbers in internal analysis to show the
  ceiling the system reaches with real source material.
* Be explicit about which corpus produced which numbers.

## 5. Fast iteration: refresh enrichment without re-embedding

Embedding the private corpus is the most expensive step (Bedrock cost
scales with chunk count). When the *chunk text* hasn't changed - for
example you only re-ran the enrichment to add new `passage_type` /
`decision_phase` tags - you can refresh just the alignment metadata:

```bash
python data_pipeline/build_vector_index.py --corpus private --metadata-only
```

This rewrites `data/corpora/private/vector_store/index_metadata.json` from
the latest knowledge base, without touching `embeddings.npy` or
`knowledge.index`.

---

## 6. Optional LLM-assisted classification (Claude Haiku)

`passage_type` and `decision_phase` are derived rule-based by default
(free, deterministic). For higher quality at a small cost set:

```bash
ENRICHMENT_USE_LLM=true python data_pipeline/build_knowledge_base.py --corpus private --profile book
```

This routes each chunk through Claude Haiku to produce stronger tags. The
classifier's output schema is closed (`prescription | framework | study | …`),
and any LLM hiccup falls back automatically to the rule-based result so
ingestion never aborts on a single bad chunk.

---

## 7. Optional LLM-as-judge reranker

Once a corpus exceeds ~3,000 chunks, FAISS top-k can become noisy. The
retriever ships with an optional Claude Haiku reranker stage gated behind
two env vars:

```bash
RAG_RERANKER=claude_haiku
RAG_RERANKER_CANDIDATES=24
```

When enabled, the retriever pulls a wider FAISS candidate pool, asks
Claude Haiku to score each candidate against the query, and keeps the
top-k by Haiku score. The reranker fails closed: any error reverts to
the FAISS-only ordering so retrieval cannot break because of reranker
issues.

Recommended default until corpus size warrants it: leave `RAG_RERANKER=none`.

---

## 8. Safety, copyright, and provenance

* The private corpus is **for personal research and private demonstration only**.
* No raw private-corpus excerpts are included in any committed file.
* `compare_versions.py` strips raw text from its public markdown output by design.
* Treat the private vector store and knowledge base as confidential
  artefacts and keep them on the laptop where the books are licensed
  for personal use.

If the project ever moves to a hosted demo, the deployed runtime should
remain pinned to `CORPUS_NAME=public`. The private corpus is a
*measurement* artefact, not a *deployment* artefact.
